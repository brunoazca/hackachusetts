## Editing direction

- **One voice for the whole film.** Record the narration in short sections, with the same mic position. Speak as a founder explaining a useful tool. No long spoken introductions or reading teammates' names.
- **One restrained music bed.** A short rising phrase gives the folklore opening scale. Lower it under the demo. Bring the opening motif back for the final logo. Keep clicks subtle and omit repetitive whooshes.
- **Use continuous screen recordings as the foundation.** Record the core path first, then cut pauses and load times. Preserve click → actual result. Do not claim elapsed-time savings from an edited sequence.
- **Move the camera only to help someone read.** Start with the whole app, then crop to one panel. Use one readable close-up at a time and let it settle before another action. Do not stretch 1080p footage through large zooms.
- **Keep the same place as the narrative anchor.** The audience should recognize it in the list, detail panel, chat context, and brief. - **Subtitle the real recorded voice.** Two lines maximum, placed clear of controls and source labels. Use short editorial overlays sparingly; the app already contains information to read.
- **No extra full-screen transitions during the demo.** The five-second bridge is the one explanatory interruption. Small labels such as “The history” and “The field brief” may sit over real footage for two seconds.

## Data, ML, and chat: what the camera must prove

**Data:** show actual rows or feature records rather than a logo wall. Four understandable input families are enough: Boston 311; code enforcement; property records; NOAA temperature. This is a selected subset of the project's sources, not a claim that every collected dataset feeds the trained model. The five-second motion bridge explains organization; it is not evidence of ingestion.

**Machine learning:** the implementation uses `HistGradientBoostingRegressor(loss="poisson")` to predict report counts per 250 m cell. `CORE` includes lagged reports, neighboring-cell history, selected leading signals, property features, calendar features, and temperature. Candidate sources such as permits or extra weather are not automatically retained model inputs. Use “gradient-boosted model” in narration and reserve the estimator name for a small optional technical label.

**Evaluation:** the stored-run evidence in the work log records top-10%-cell report capture of **64.29% versus 54.33%** for the four-week baseline, and mean absolute error of **0.07518 versus 0.07132**. These are historical stored metrics, not a fresh rerun or a verified reading of today's deployed panel. The model improved hotspot concentration in that run while average error was worse. Never call 64% “accuracy,” describe the result as a 64% improvement, or claim the model wins on every metric. Use actual values from the same run being shown; do not hardcode old values over a newer screen. A concise optional voice line, only after matching that run, is: “Its top-ranked tenth of blocks captured sixty-four percent of reports, versus fifty-four for the baseline. Average count error was slightly worse.” The generic evaluation narration already fits the slot without requiring a specific result.

**Chat:** demonstrate a real question → data retrieval → map connection → answer → citation. A chat title, blinking cursor, or prewritten bubble does not prove the flow. Use the ML panels for forecast explanation. If a returned feature chip moves the map, show the user's click; do not edit it to imply an automatic action.
